# 갤럭시 3D 사진·영상 매직아이 뷰어 개발 계획

Oct 5, 2026 · @은호당

## 목표와 범위

갤럭시로 찍은 3D 영상과 3D 사진을 왼눈·오른눈 두 장으로 풀어 나란히(SBS) 띄우고, 평행법과 교차법으로 맨눈 입체시를 하게 만든다. PC 브라우저와 안드로이드 폰 가로 화면에서 같은 앱이 돌아간다. 모든 처리는 사용자 기기 안에서 끝나고, 파일을 서버로 올리지 않는다.

만드는 것

- 변환: 3D 영상을 SBS mp4로, 3D 사진을 SBS jpg·png로 푼다. 좌우 순서는 평행법용(LR)과 교차법용(RL)을 모두 낸다.
- 보기: 평행·교차 전환, 크기·간격·상하 정렬 조절, 전체화면 가로 고정, 융합 보조점.
- 일괄 처리: 폴더를 통째로 넣으면 한 번에 변환한다(PC).

이번 범위에서 빼는 것

- 2D 사진을 AI로 3D로 바꾸는 기능(깊이 추정)
- VR 헤드셋 재생, SBS를 MV-HEVC로 되돌리는 인코딩
- 아이폰 공간 사진·영상 정식 지원(구조가 같아 덤으로 되면 받아들이되 목표로 잡지 않는다)
- iOS Safari 최적화

열린 질문: 촬영 기종(S25 계열인지, 다른 모델인지)과 One UI 버전. 파일 구조가 기종·버전마다 다를 수 있으니 Phase 0에서 함께 기록한다.

## 입력 파일: 알려진 것과 확인할 것

영상은 MV-HEVC, 사진은 HEIC로 저장된다는 정도만 알려져 있고, 좌우가 파일 안 어디에 들어 있는지는 아직 아무도 공개적으로 확인하지 않았다. 그래서 코드보다 실제 파일 해부가 먼저다.

| 항목 | 지금까지 알려진 내용 | 출처 | Phase 0에서 확인할 것 |
| --- | --- | --- | --- |
| 3D 영상 코덱 | MV-HEVC. 폰 갤러리에서는 평면으로만 보이고, 3D는 MV-HEVC를 재생하는 XR 기기에서 보인다 | Sammyfans 보도 | 컨테이너(mp4·mov), 레이어 2개 여부, view id, 좌우 메타데이터, 오디오 트랙 |
| 3D 영상 해상도 | 한쪽 눈당 1920×1080 (S25 Ultra) | ImmerVR 측정, stereoscopy.blog 인용 | 프레임레이트, HDR 여부, 회전 메타데이터 |
| 3D 사진 형식 | HEIC, 한쪽 눈당 4000×3000 (S25 Ultra) | 같은 출처 | 이미지 아이템 개수, 기본(primary) 이미지가 평면용인지 한쪽 눈인지 |
| 좌우 찾는 법 | 애플 공간 사진은 0번 이미지가 좌안이라는 보장이 없고, 평면 기기용 단안 이미지가 0번에 들어가기도 한다. 좌우는 스테레오 페어 그룹 정보로 찾는다 | 애플 개발자 포럼 답변 | 갤럭시 HEIC에 같은 그룹(ster)이 있는지, 없으면 무엇으로 좌우를 표시하는지 |
| 폰 안 디코딩 | 안드로이드 Media3의 MV-HEVC 재생은 MV-HEVC 디코더를 갖춘 안드로이드 XR 기기를 전제로 한다 | Android Developers 문서 | 폰 기본 디코더가 두 번째 시점을 내주는지(기대하지 않는다) |

출처들은 10월 5일 이 대화에서 검색으로 확인한 내용이다. 표의 수치는 한 기종 측정값이니, 은호당님 파일로 다시 잰 값을 우선한다.

## 아키텍처: 변환과 보기를 떼어 놓는다

무거운 MV-HEVC 디코딩은 PC의 FFmpeg가 가장 빠르고 확실하고, 보기는 PC와 폰 어디서나 열리는 웹 앱 하나면 된다. 안드로이드 네이티브 앱은 Phase 4가 실패할 때만 꺼내는 예비안이다.

&#91;embedded content: 구조 · 입력 2종, 변환 경로 2개, 뷰어 1개\]

두 변환 경로 모두 좌우 검산을 거친 SBS 파일을 내고, 뷰어는 SBS만 받는다. 변환 방식이 바뀌어도 뷰어는 손댄 필요가 없다.

## 단계별 작업

다섯 단계로 나누고, 각 단계는 통과 조건(게이트)을 넘어야 다음으로 간다. Phase 0\~2만 끝나도 PC로 변환하고 폰으로 보는 흐름이 완성된다. Phase 3\~4는 폰 하나로 끝내기 위한 확장이다.

1. Phase 0: 파일 해부
   - 준비물: 3D 사진 3장, 3D 영상 2개(각 10초 안팎). 가까운 물체와 먼 배경이 함께 잡힌 장면이어야 좌우 판별이 쉽다.
   - 옮기는 법: USB 케이블이나 Quick Share로 원본 그대로. 카카오톡·메신저는 재압축하면서 두 번째 시점을 버릴 수 있으니 쓰지 않는다.
   - 할 일: ffprobe(FFmpeg 7.1 이상)로 영상 스트림·사이드데이터를, heif-info와 exiftool로 사진 아이템·그룹·메타데이터를 덤프한다. 영상은 `ffmpeg -view_ids -1 -i in.mp4 -filter_complex "[0:v:view:0][0:v:view:1]hstack"` 계열 명령으로 두 시점을 뽑아 본다. 이 문법은 7.1 기준이라 실행 결과로 다시 확인한다.
   - 산출물: `docs/FORMAT.md`(실측 구조 보고서, 명령과 원본 출력 포함), 좌우 개별 PNG 샘플.
   - 게이트: 사진과 영상 모두 좌우 두 장을 무손실로 꺼내고, 어느 쪽이 왼눈인지 판정 근거까지 확보.
2. Phase 1: PC 변환 엔진(Python CLI)
   - 명령 예시: `g3d convert <파일|폴더> --order lr|rl|both --out <폴더>`
   - 영상은 시스템 FFmpeg를 subprocess로 호출하고, 오디오와 촬영일 메타데이터를 보존한다. 출력은 호환성을 위해 H.264 mp4.
   - 사진은 libheif 바인딩(pillow-heif 또는 pyheif 계열, Phase 0 결과로 선택)으로 아이템별 디코딩 후 좌우를 이어 붙인다.
   - 파일명 규칙: `원본명_SBS_LR.jpg`(평행법), `원본명_SBS_RL.jpg`(교차법).
   - 게이트: 샘플 전부 변환 성공, 좌우 판별 자동 테스트 통과.
3. Phase 2: 웹 뷰어(PWA, SBS 입력)
   - SBS 파일(Phase 1 산출물이든 다른 SBS든)을 열어 보는 앱. 정적 사이트로 GitHub Pages에 올리고 서비스 워커로 오프라인 동작.
   - 보기 요건은 아래 뷰어 UX 절을 따른다.
   - 게이트: 은호당님이 폰 가로 전체화면과 PC 모니터에서 평행법·교차법 둘 다 융합에 성공.
4. Phase 3: 브라우저 안 사진 변환
   - libheif 웹어셈블리 빌드로 HEIC를 브라우저에서 바로 풀어, 폰만으로 사진을 처리한다.
   - 게이트: 폰 크롬에서 4000×3000 두 장 디코딩이 메모리 오류 없이 10초 안에 끝남.
5. Phase 4: 브라우저 안 영상 변환(실험)
   - FFmpeg 7.1 이상으로 직접 빌드한 ffmpeg.wasm에 MV-HEVC 디코딩을 넣는다. 소프트웨어 디코딩이라 느릴 것을 전제로, 변환 후 감상 구조로 간다.
   - 게이트: 10초 영상 변환이 폰에서 2분 안. 넘으면 이 단계는 접고, 필요할 때만 안드로이드 네이티브 앱(Kotlin + NDK FFmpeg)으로 우회한다.

## 뷰어 UX: 매직아이용 요건

화면 설계의 기준은 두 그림 중심 사이의 실제 거리(mm)다. 평행법은 이 거리가 눈 사이 거리보다 좁아야 하고, 성인 눈 사이 거리 평균은 약 63mm다(Dodgson, 2004). 폰을 가로로 눕혀 화면을 반씩 나누면 중심 간격이 70mm를 넘기 쉬워, 그대로 두면 평행법 융합이 안 된다.

| 기능 | 요건 | 이유 |
| --- | --- | --- |
| 평행·교차 전환 | 버튼 한 번, PC는 S 키. 좌우 이미지를 맞바꾼다 | 두 방식은 좌우 순서만 다르다 |
| 실측 보정 | 첫 실행 때 신용카드(가로 85.60mm)를 화면에 대고 막대 길이를 맞춰 px/mm를 저장 | CSS 픽셀은 기기마다 실제 크기가 달라 mm를 알 수 없다 |
| 크기·간격 슬라이더 | 그림 폭과 중심 간격을 mm로 표시. 평행법 기본값은 중심 간격 60mm | 평행법은 63mm 아래, 교차법은 넓을수록 편하다 |
| 상하 정렬 | 한쪽 이미지를 ±픽셀 단위로 위아래 이동 | 상하 어긋남은 입체 피로의 주된 원인이다(Lambooij 외, 2009) |
| 좌우 이동(창 조절) | 두 이미지를 서로 반대 방향으로 이동해 화면 깊이 위치 조절 | 물체가 화면 앞으로 튀어나와 불편할 때 뒤로 민다 |
| 융합 보조점 | 각 이미지 위에 점 하나씩. 점 두 개가 셋으로 보이면 융합 완료 | 처음 매직아이를 하는 사람에게 가장 빠른 길잡이 |
| 가로 고정 | 전체화면 진입 후 Screen Orientation API로 가로 잠금, Wake Lock으로 화면 꺼짐 방지 | 안드로이드 크롬은 전체화면에서만 방향 잠금을 허용한다 |
| 영상 처리 | video 요소를 숨기고 requestVideoFrameCallback으로 매 프레임을 캔버스 좌우에 그린다. 소리는 video 요소에서 낸다 | 사진과 영상에 같은 전환·정렬·이동 기능을 적용하려면 픽셀을 직접 다뤄야 한다 |
| 확인용 보조 모드(선택) | 적청 애너글리프, 좌우 번갈아 깜빡이는 위글 | 매직아이가 안 될 때도 입체 여부를 눈으로 확인 |

설정값(px/mm, 기본 모드, 간격)은 기기 브라우저 저장소에 남겨 다음 실행 때 그대로 쓴다.

## 좌우 판별과 완료 기준

좌우를 메타데이터에만 맡기지 않고 영상 자체로 검산한다. 좌우가 뒤집히면 입체가 안쪽으로 꺼지는 역입체가 되는데, 눈으로 보면 "뭔가 이상하다" 정도로만 느껴져 놓치기 쉽다.

판별 원리: 두 렌즈가 나란히 놓인 카메라에서는 같은 물체가 왼눈 이미지에서 더 오른쪽에 찍힌다. 그래서 두 시점 사이에서 특징점을 매칭해 x좌표 차이(왼쪽 후보 − 오른쪽 후보)의 중앙값이 양수면 순서가 맞다. 가까운 물체일수록 이 차이가 크다.

- 구현: OpenCV ORB 매칭 + RANSAC으로 오매칭 제거, 수평 시차 중앙값과 수직 시차 중앙값을 함께 기록한다.
- 수직 시차 중앙값이 0에서 멀면 렌즈 정렬이 틀어진 기종일 수 있으니, 그 값을 뷰어 상하 정렬의 기본값으로 쓴다.
- 영상은 앞·중간·끝 프레임 세 장으로 판정하고, 세 결과가 엇갈리면 경고를 띄운다.

완료 기준

- [ ] 샘플 사진·영상 전부에서 좌우 판별 자동 테스트 통과
- [ ] 변환 결과의 한쪽 눈 해상도가 원본과 같음(사진 4000×3000, 영상 1920×1080 기준, Phase 0 실측값으로 교체)
- [ ] 영상 SBS에 원본 오디오와 길이가 그대로 남음(±1프레임)
- [ ] 폰 가로 전체화면에서 평행법, PC 모니터에서 교차법으로 은호당님 본인이 융합 확인
- [ ] 네트워크를 끊은 상태에서도 웹 뷰어가 동작(파일이 밖으로 나가지 않음을 함께 증명)

## 위험 요소와 대응

가장 큰 위험은 갤럭시 파일 구조가 공개 규격과 다를 가능성이고, 그래서 Phase 0을 게이트로 묶었다.

| 위험 | 일어나면 | 대응 |
| --- | --- | --- |
| 갤럭시 HEIC에 스테레오 그룹이 없거나 자체 방식으로 좌우를 표시 | 사진 좌우를 못 찾음 | Phase 0에서 아이템을 전부 뽑아 시차 판별로 좌우를 정하고, 형식별 어댑터로 분리 |
| One UI 업데이트로 파일 구조가 바뀜 | 잘 되던 변환이 깨짐 | 파서 앞단에 형식 감지 단계를 두고, 모르는 구조면 덤프를 남기고 멈춤 |
| FFmpeg의 MV-HEVC 디코딩 버그·미지원 기능(HDR 등) | 두 번째 시점이 깨지거나 색이 틀어짐 | FFmpeg 버전을 고정하고 샘플 회귀 테스트로 업그레이드 검증 |
| ffmpeg.wasm이 폰에서 너무 느리거나 메모리 부족 | Phase 4 실패 | 영상 변환은 PC에 남기고 뷰어만 폰에서 쓴다 |
| 전송 과정 재압축 | 3D 정보가 사라진 파일이 들어옴 | 입력 단계에서 시점이 하나뿐이면 "원본으로 다시 옮기세요" 안내 |
| 렌즈 간격이 좁아 입체감이 약함 | 기대보다 밋밋함 | 하드웨어 한계라 코드로 못 고친다. 가까운 피사체(1\~3m) 촬영을 사용 안내에 넣는다 |
| 라이선스 | FFmpeg에 libx264를 넣으면 GPL | 개인용이면 문제없음. 배포할 계획이 생기면 그때 재검토 |

## Claude Code·Codex 작업 규칙

이 절은 에이전트에게 그대로 붙여 넣는 지시문이다. 저장소 루트의 CLAUDE.md 또는 AGENTS.md에 넣는다.

```markdown
# galaxy3d-viewer 작업 규칙

## 저장소 구조
- core/    Python CLI 변환 엔진 (Phase 1)
- web/     정적 PWA 뷰어 (Phase 2~4), GitHub Pages 배포
- docs/    FORMAT.md(실측 파일 구조), 단계별 보고서
- samples/ 사용자 원본 파일. .gitignore로 커밋 금지

## 원칙
1. 파일 구조를 추측하지 말 것. Phase 0에서 ffprobe·heif-info·exiftool로 실측하고, 명령과 원본 출력을 docs/FORMAT.md에 그대로 붙인다.
2. 실행하지 않은 것을 확인했다고 쓰지 말 것. 테스트 결과는 실제 로그로 보고한다.
3. 게이트를 넘기 전에는 다음 Phase로 가지 않는다. 각 Phase 끝에 데모 방법과 한 문단 보고를 남긴다.
```
